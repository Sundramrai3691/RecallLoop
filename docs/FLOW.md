# Request and function flows

This is a source-derived map of the current implementation. HTTP routes are mounted under `/api` in `server/src/routes/index.ts`; route modules show authentication, controllers delegate to services, and SQL is issued through repositories or service queries using the shared `pg` pool. Names below refer to current source symbols. Error responses pass through `server/src/middleware/errorHandler.ts`.

## Runtime request path

`client/src/pages/*` / `client/src/hooks/*` → `client/src/api/client.ts` → Vite `/api` proxy → `server/src/app.ts` (`express.json`, CORS) → `server/src/routes/index.ts` → route middleware (`requireAuth` where declared) → controller → service → repository/parameterized SQL → PostgreSQL → JSON response → client page state.

`server/src/index.ts` calls `connectDatabase()` (`SELECT 1`) before `app.listen`. A refused PostgreSQL connection prevents the API from listening; Vite can still start, but its `/api/*` proxy calls then fail. Startup does not run migrations automatically. Use the setup sequence in the root README.

## HTTP surface

All endpoints use JSON. `requireAuth` routes derive `userId` from the verified token; curated catalog reads and health are public. Learner-specific roadmap reads require authentication.

## Important workflows

| Workflow | Call chain and effects | Failure / transaction notes |
|---|---|---|
| 1. Register | `authRouter` → `registerHandler` → `registerUser` → `userRepository`; password hashed before insert; session token returned. | Duplicate/invalid credentials become API errors; no cross-domain transaction. |
| 2. Login/current user | `loginHandler` → `loginUser`; later `requireAuth` verifies bearer token and `/auth/me` → `getCurrentUser`. | Invalid/expired token rejected by auth middleware; user ownership comes from claims. |
| 3. Create goal and skills | `goalController` → `goalService.createGoal/createSkill` → goal/learner-skill repositories. | Goal ownership is checked before nested operations. |
| 4. Choose starting point | `startingPointController` → starting-point service queries goal, canonical requirements and learner state; Trust Me can use baseline assessment path. | Missing or foreign goal is not exposed as another user's data. |
| 5. Baseline assessment | `baselineController` → `baselineService.createBaseline/submitBaselineQuestion`; one question is created per eligible canonical concept, tied to one stable `knowledge_point_id`, and its answer is evaluated against the concept's distinct required points. The answer/evidence, completion aggregate, and learner knowledge state are committed together. | No concept-by-point join fanout; report point counts are unique within each canonical concept. Submission locks the assessment row and conditionally writes only a pending question, preventing duplicate overwrites and serializing concurrent final answers. Assessed rows with no submitted point evidence retain `observed_mastery = NULL`; self-declared mastery remains a separate field. |
| 6. Read canonical knowledge and roadmap | `knowledgeController` → `knowledgeService`; public catalog endpoints read shared role/skill/topic/concept/point/source/resource data; authenticated roadmap endpoints add user-scoped completed-session, submitted-recall and submitted-baseline evidence. | Catalog IDs remain shared reference data. Role roadmap returns direct prerequisite edges without recursive traversal; source-less nodes remain visible. Point objects retain canonical IDs and repeated joined rows are collapsed by ID, not display text. Migration `015` repairs duplicate seed rows and adds the corresponding per-concept normalized-statement/metadata uniqueness rule. |
| 7. Create study session and extract concepts | `studySessionController.createStudySessionHandler` → session service validates topic/source URL, UUID formats and canonical topic/concept parentage, requires notes → evaluator extracts and validates concepts before session persistence → session stores optional canonical IDs and normalized personal concepts. | Topic, optional `source_url`, and supplied `raw_material` are separate; source URLs are not fetched and URL tokens are removed before extraction. Extracted names, descriptions and knowledge-point statements containing URL tokens are rejected before persistence, so they cannot flow into generated question prompts. A personal concept maps to the selected canonical concept only on exact normalized name equality; custom topics and other extracted concepts remain unmapped. Existing history is not backfilled. Provider/schema/content errors happen before a session is written. |
| 8. Complete study session | `completeStudySessionHandler` → `studySessionService.completeStudySession` → transaction updating session, creating immediate recall/review work and recording event. | `withTransaction` rolls back grouped writes on error. |
| 9. Start assessment | `assessmentController` → `assessmentService.createAssessment` → deterministic concept/point blueprint → validated question records → assessment session and attempts in PostgreSQL. | Free recall targets the point named by its prompt. MCQs require a curated key and misconception-based distractors; concepts without one use recall instead. Mode/concept ownership validated; assessment writes are transactional. |
| 10. Get/reveal recall hint | `recallController` → `recallService.getRecall/revealRecallHint` → owned attempt/question read or atomic hint counter update. | Hidden hints are not included until revealed; no hint beyond configured allowance. |
| 11. Submit MCQ answer | `submitRecallHandler` → `submitRecall` → persisted answer key grading (`evaluateMcq`) → result/evidence persistence, mastery and review schedule update. | Attempt must belong to user and be pending; derived coverage comes from knowledge-point outcomes. |
| 12. Submit free-form recall | Same controller/service → for structured questions validate each submitted `partId`, call the existing evaluator separately with that part's rubric, and merge only validated point results; legacy questions still evaluate one answer. Coverage is derived from all point statuses. | Evaluation occurs before transaction. The transaction persists attempt plus part-keyed answers, evaluation and point results, per-point learner states, dimension results, aggregate concept mastery, review state and learning events. A point gets a canonical point FK only when exactly one point under the session's selected canonical concept matches its normalized statement exactly; fuzzy or ambiguous labels remain unmapped. Provider/validation failure writes nothing; duplicate submissions lose the conditional pending-attempt update and cannot add evidence. |
| 13. Read learner model | `learnerController` → `learnerModelService` summary/weak concepts/weak skills → user-scoped aggregate queries over submitted attempts, evaluations, concepts, skills and review states. | Concepts without a submitted attempt remain new/null. Point states are written from validated evaluation results inside the recall transaction; report dimensions without evidence stay null. |
| 14. Generate daily plan | `goalController.generateGoalPlanHandler` → `goalService.generateGoalPlan` → candidate selection/budget fitting → plan repositories replace future planned tasks. | Task replacement runs transactionally; budget constrained by API validation and migration checks. |
| 15. Read today's plan | `GET /plan/today` → `goalService.getTodayPlan` → active plan/tasks and due review data → serialized task list. | Empty state returned when no active plan; owner scope enforced. |
| 16. Update plan task | `PATCH /plan/tasks/:id` → `goalService.updatePlanTask` → owned task status update and event where implemented. | Invalid status or foreign task rejected. |
| 17. Get dashboard | `dashboardController` → `dashboardService.getDashboard` → user-scoped aggregates/joins for goals, today's tasks, recall, learner state. | Query failure becomes common API error; no write. |
| 18. Recommend resources / learning pack | `resourceController` → resource recommendation or pack service → catalog concept link, learner signals, goal and time-estimate ranking. | Deterministic ranking; recommendation explanations omit uncalibrated trust/freshness/coverage percentages; no write to learner state. Resource titles use stored metadata with a safe provider fallback, and the original URL remains the link target. |

Study creation accepts a topic string, optional HTTP(S) `sourceUrl`, supplied text, and optional canonical topic/concept IDs separately. URL-only topic/material is rejected with a correction message. No webpage or video transcript fetch exists in this path. Extraction failure is returned before session insertion; successfully extracted concepts are validated and normalized before persistence. The client retains topic, source link and notes on failure, and distinguishes a confirmed provider rejection from an uncertain network outcome. Migration `013_study_session_source_url.sql` stores optional provenance; migration `014_canonical_study_handoffs.sql` stores the optional catalog handoff and canonical point evidence links.
| 19. Ingest grounding source | `groundingController` → `ingestGroundingSource` → hash and deterministic chunking → embedding provider → source/chunk repositories. | Source processing status/error recorded; chunk insertion is transactional; only user-provided text is ingested (no URL fetch). |
| 20. Remediate and verify a gap | `createRemediationHandler` → `createGroundedRemediation` → attempt/point evidence → user-scoped retrieval/ranking → validated generator → persist remediation; verification creates targeted assessment/recall attempt and later updates status. | Low relevance or unsupported generation does not fabricate evidence; source retrieval scoped by owner; relevant grouped writes use transactions. |
| 21. Roadmap-to-study handoff | Knowledge role page selects a canonical topic or concept and links to `/study/new` with its UUIDs plus a local roadmap return path → `NewStudyPage` keeps those IDs with the selected suggestion → authenticated study-session POST validates parentage and saves IDs. The roadmap aggregates completed sessions as `studied` and submitted baseline/recall evidence as `assessed`; canonical point evidence is linked only by a unique exact statement match. | Completion is not mastery. Custom text stays unmapped; the learner can return to the role/topic after study and recall. No fuzzy mapping or inferred score is stored. |

The service names above are confirmed in `server/src/services`. Not every single SQL query has a repository wrapper; several domain services query the shared database module directly. Transaction details are implemented by `server/src/db/postgres.ts::withTransaction` and the call sites.

Canonical roadmap points originate in `knowledge_points`, not from learner concept extraction. The HTTP caching duplicate was traced to `002_seed_knowledge.sql` replaying its point insert with `ON CONFLICT DO NOTHING` while the table had no matching unique index. Migration `015_deduplicate_canonical_knowledge_points.sql` records each duplicate group and its foreign-key reference counts in `canonical_knowledge_point_deduplication_audit`, remaps baseline, recall and learner point references, removes only same-concept normalized statements with identical importance/difficulty metadata, retains metadata-conflict groups for review, and adds an idempotency index. The role roadmap aggregates any repeated query rows by canonical point ID; it does not merge different IDs based on similar display text.

LLM extraction and free-form evaluation use `LLM_PROVIDER`; grounding source ingestion and retrieval use `EMBEDDING_PROVIDER`; structured grounded generation uses `REMEDIATION_PROVIDER`. The accepted values and Gemini-compatible endpoint example are documented in [Architecture](ARCHITECTURE.md). Selected real providers do not fall back to mock on missing credentials, provider failures, or malformed output. The compatible chat adapter inspects only allowlisted structured error fields: authentication/access failures, quota or billing exhaustion, transient 429 rate limiting, upstream 5xx, request rejection, timeout and malformed response remain distinct. Transient 429/5xx responses get at most one retry; a valid `Retry-After` of one second or less is honored for that retry, while longer delays are returned immediately as a safe `Retry-After` header plus `LLM_RATE_LIMITED` and seconds metadata. Exhausted quota, auth/access, and permanent request failures are not retried. Provider error bodies, credentials and authorization headers are not logged or returned. A transient upstream HTTP 429 is exposed by RecallLoop as HTTP 429; quota/billing exhaustion remains HTTP 503 because waiting alone cannot restore quota.

When free-form recall evaluation fails, it happens before the submission transaction: the answer is not persisted as evaluated, `submitted_at` stays null, and no evaluation or learner-state evidence is written. The client retains the response and confidence and identifies the attempt as pending for classified provider failures. If a request outcome is uncertain, it fetches the attempt before presenting a retry; an already-submitted attempt opens its result instead of being resubmitted. Conditional pending-attempt update and the existing transaction preserve duplicate-submit idempotency. Study extraction also precedes session insertion, so classified provider failures leave no study row; URL-bearing extracted learner-facing content is likewise rejected before a row is written. The form remains populated. Neither workflow substitutes mock output after a real-provider failure. Grounded remediation validates provider JSON and rejects URL tokens in generated learner-facing content; source links remain available through their separately stored provenance fields.

### Structured question answer contract

Questions that intentionally assess multiple required points can return `questionData.parts` (`id`, `label`, `prompt`, `knowledgePoints`, and `rubric`). The existing `POST /api/recalls/:id/submit` accepts `answers: [{ partId, answer }]` with the existing confidence/hint fields. The server rejects unknown and duplicate IDs, fills omitted parts as unanswered, and does not call the evaluator for blank parts. Blank parts receive `missing` evidence. MCQs continue through deterministic answer-key grading. Existing single-answer requests remain valid for legacy questions.
