# PostgreSQL Cutover Report

## 1. Why MongoDB was replaced

MongoDB was sufficient for the MVP, but the current goal, plan, learner, canonical knowledge, baseline, and resource domains require explicit relational ownership, foreign keys, uniqueness, transactional multi-write flows, and normalized recall evaluation data. PostgreSQL is the intended single runtime authority. MongoDB is not an acceptable fallback or dual-write store.

## 2. Current PostgreSQL architecture

`Express -> domain services -> PostgreSQL data access -> pooled pg connection -> PostgreSQL`. SQL migrations live under `server/migrations/`. The Phase 3 knowledge and baseline schema is present, with a curated idempotent seed. `pgvector` is not included.

## 3. Mongo to PostgreSQL mapping

See [PHASE3_MIGRATION_PLAN.md](PHASE3_MIGRATION_PLAN.md) and [POSTGRES_CUTOVER_AUDIT.md](POSTGRES_CUTOVER_AUDIT.md). Existing document collections map to relational users, goals, learner skills, plans, tasks, study sessions, personal concepts, recall attempts, normalized evaluations, review states, and learning events.

## 4. Table relationships

Users own goals, learner skills, plans, sessions, personal concepts, attempts, review states, tasks, and events. Canonical roles own canonical skills, topics, concepts, knowledge points, prerequisites, sources, and resources. Personal concepts and canonical concepts remain separate.

## 5. Repository/data-access architecture

The target boundary is repository interfaces consumed by domain services and implemented with parameterized PostgreSQL queries. Authentication, goals/plans, study/concepts, recall/review, learner, dashboard, events, canonical knowledge, baseline, and resources now use PostgreSQL data-access modules.

## 6. Transaction boundaries

Study completion must atomically update the session, create recalls, create/update review states, and append events. Recall submission must atomically persist the attempt, normalized evaluation/results, mastery update, review state, and events. Plan replacement and baseline submission also require focused transactions.

## 7. Authentication and ownership

JWT middleware remains the identity boundary. PostgreSQL rows use `user_id` ownership foreign keys. Services must derive ownership from `req.user.id`; clients must never provide authoritative ownership IDs.

## 8. Recall evaluation persistence

The target schema separates `recall_attempts`, `recall_evaluations`, and `recall_knowledge_point_results`. Status-derived coverage remains authoritative; the LLM's numeric coverage is ignored. Evaluation version, feedback, mistakes, strengths, and missing concepts are retained.

## 9. Planner persistence

`plans` is authoritative for a plan window and `plan_tasks` is authoritative for learner-facing work. `review_states` remains authoritative for recall timing. Plan generation must use one transaction for plan/task replacement and preserve due-recall references.

## 10. Canonical knowledge persistence

Canonical roles, skills, topics, concepts, points, prerequisites, sources, role mappings, resources, and resource coverage are PostgreSQL-backed and seeded by `002_seed_knowledge.sql`.

## 11. Baseline persistence

`baseline_assessments`, `baseline_questions`, and `learner_knowledge_states` distinguish assessed evidence, self-declared knowledge, confidence, and recommended starting concepts. Baseline uses the existing evaluator rather than a second evaluator.

## 12. Migration utility

A production cutover still needs `scripts/migrate-mongo-to-postgres.*` or an equivalent one-time utility. It must export Mongo rows, create explicit ID mappings, insert parents before children, validate foreign keys, report counts/orphans, and fail clearly on invalid records.

## 13. ID mapping strategy

Mongo ObjectIds must be stored in a source-to-target mapping table or durable mapping file. UUIDs are generated by PostgreSQL; dependent rows resolve through the mapping. No ObjectId-to-UUID string cast is permitted.

## 14. Test strategy

Pure evaluator, scheduler, recommendation, and repository unit tests should run without a database. Integration tests must use an isolated PostgreSQL database. The existing Mongo memory tests are still legacy tests and must be replaced during the final cutover.

## 15. PostgreSQL setup

```bash
docker compose up -d postgres
npm run db:migrate -w server
npm run db:seed -w server
```

The current migration command applies schema and seed together. A separate seed command can be split once the runtime cutover repositories land.
